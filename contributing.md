# Contributing Guide

This repository supports two closely related use cases:

1. A public, forkable template for building a CV using LaTeX + Lua + JSON.
2. A private working branch that contains personal data and is synchronized with Overleaf.

To support both without constant merge conflicts or accidental data leaks, this repository uses a two-branch workflow combined with a custom merge strategy for data files.

This document explains that workflow step by step.

----------------------------------------------------------------

Repository Structure Overview

.
├── lua/                 # Lua renderers (shared)
├── tex/ / main.tex      # LaTeX sources
├── data/                # JSON data files (branch-specific)
├── .gitattributes       # Merge rules (IMPORTANT)
├── README.md
└── CONTRIBUTING.md

Key idea:
- Code is shared across branches
- Data differs by branch
- Git is configured so that data files never cause merge conflicts

----------------------------------------------------------------

Branches and Their Roles

main — Public Template Branch
- Contains example JSON data
- Safe to fork and share
- Represents the canonical public version of the codebase
- This is what new users see by default

cv — Personal / Working Branch
- Contains real CV data
- Connected to Overleaf
- Used for day-to-day authoring
- Includes frequent, sometimes noisy commits generated by Overleaf

IMPORTANT:
Never merge cv into main blindly.
All merges into main should be intentional and reviewed.

----------------------------------------------------------------

Why a Special Merge Strategy Is Used

Data files in data/*.json are:
- branch-specific
- semantically incompatible across branches
- expected to differ permanently

To prevent merge conflicts and accidental data leakage, this repository uses a custom merge rule.

----------------------------------------------------------------

.gitattributes (Critical File)

At the repository root:

data/*.json merge=ours

This tells Git:
When merging, always keep the version of data/*.json from the branch being merged INTO.

One-time setup requirement (run locally once):

git config merge.ours.driver true

After this:
- Code merges behave normally
- Data files are automatically protected

----------------------------------------------------------------

Typical Workflows

Workflow A: Bringing Code Changes from main → cv

Use this whenever:
- the template code is updated
- Lua renderers change
- LaTeX structure is improved

Commands:

git checkout cv
git pull origin cv
git merge origin/main
git push origin cv

What happens:
- All code updates are merged
- Your real data/*.json files stay untouched
- No merge conflicts
- Overleaf continues to work normally

----------------------------------------------------------------

Workflow B: Publishing Selected Changes from cv → main (Careful!)

This happens when:
- you improved a renderer
- you fixed documentation
- you want template users to benefit

Because Overleaf commits may mix data and code changes, you must be deliberate.

----------------------------------------------------------------

Recommended Pattern: Merge Preview + Reset Data

Step 1: Update main

git checkout main
git pull origin main

Step 2: Merge cv WITHOUT committing

git merge cv --no-commit --no-ff

Step 3: Reset data files back to main’s versions

git checkout --ours data/
git add data/

Step 4: Stage intended changes only

git add lua tex README.md

Step 5: Commit and push

git commit -m "Improve presentation renderer and documentation"
git push origin main

Result:
- Public branch updated safely
- Private data never leaked
- History stays clean and understandable

----------------------------------------------------------------

Alternative: Cherry-picking Clean Commits

If a commit on cv is pure code (no data touched):

git checkout main
git cherry-pick <commit-hash>
git push origin main

This works well when Overleaf commits are small and focused.

----------------------------------------------------------------

Important Rules and Best Practices

DO:
- Merge from main into cv frequently
- Treat main as a curated release branch
- Write clear commit messages when updating main
- Assume Overleaf commits are noisy and temporary

DO NOT:
- Automatically merge cv into main
- Force-push shared branches
- Store real data in main
- Rely on Overleaf for branch management

----------------------------------------------------------------

Why This Workflow Is Used

This approach:
- Keeps forks clean and usable
- Preserves full history of personal data
- Plays nicely with Overleaf’s limitations
- Avoids constant manual conflict resolution
- Uses Git features as designed (merge drivers, not hacks)

This is a deliberate, mature tradeoff between automation and control.

----------------------------------------------------------------

For Contributors and Forks

If you fork this repository:
- You only need main
- You can replace example data with your own
- You do not need the cv branch
- You do not need Overleaf integration

If you later create your own private branch, you are encouraged to reuse this pattern.

----------------------------------------------------------------

Questions or Confusion

If you find yourself unsure:
- which branch you’re on
- whether a merge is safe
- or why data didn’t change

Pause, check git status, and refer back to this document.

----------------------------------------------------------------

Final Note

This repository is intentionally structured to support long-running personal scholarly work.
If something feels cautious, that is by design.
